= Running an application in development mode with `mn:dev`

`mn:dev` runs the application through the development launcher of Micronaut Core 5.3 (`micronaut-dev`): sources are
compiled inside the running JVM and the application is restarted on a fresh class loader, with the singletons a
retention policy names kept alive, or, for an edit that only changed method bodies, the classes are redefined in place.
`mn:dev` replaces `mn:run`, which recompiles through Maven and relaunches the JVM, and which is deprecated for removal
in Micronaut 6.

:toc:

== Usage

[source,bash]
----
$ mvn mn:dev
----

The goal writes the manifest the launcher reads into `target/micronaut-dev/dev.properties`, from the project model: the
runtime, compile and annotation processor classpaths (the processor path from the `maven-compiler-plugin`'s
`annotationProcessorPaths`), the source and resource directories, the compiler options as the compiler plugin is
configured (`-parameters`, the release, the encoding and `compilerArgs`), and the settings below. The outputs of the
project and of the reactor projects it depends on are the reloadable tier; the modules are the parent tier. The
launcher compiles Java with `javac` and Groovy with the project's Groovy. Embedded Kotlin is not offered on Maven.

== Settings

[cols="2,1,4"]
|===
|Property |Default |Meaning

|`mn.dev.strategy` |`auto` |`restart`, `reload` or `auto`.
|`mn.dev.compile` |`embedded` |`embedded` compiles inside the development JVM; `build-tool` lets this goal compile through Maven, as `mn:run` does, and tell the launcher through `target/micronaut-dev/reload`.
|`mn.dev.incremental` |`true` |Whether the embedded compilers compile incrementally.
|`mn.dev.retain` | |Types whose singletons are kept across a restart, comma separated.
|`mn.dev.livereload` |`true` |Adds `micronaut-dev-livereload` to the launcher's classpath, which starts the LiveReload server.
|`mn.dev.livereload.port` |`35729` |The LiveReload port.
|`mn.dev.livereload.injectScript` |`true` |Whether the client script is appended to HTML responses; `false` for users of a browser extension.
|`mn.dev.bindLoopback` |`true` |Whether the application link:#bind-loopback[listens on `localhost`] by default; `false` to reach it from a phone or a container.
|`mn.dev.controlPanel` |`true` |Adds link:#control-panel[Micronaut Control Panel] to the development runtime.
|`mn.dev.manifestOnly` |`false` |Writes the manifest and stops, for a build that launches the JVM itself.
|===

`mn.debug`, `mn.debug.suspend`, `mn.debug.port`, `mn.debug.host`, `mn.jvmArgs`, `mn.appArgs` and the test resources
settings work as they do for `mn:run`.

== Reactor dependencies

The outputs of the reactor projects the runnable one depends on are reloadable too, and their sources are compiled by
the launcher into the runnable project's output, with the runnable project's compiler settings. A reactor whose modules
need different compiler settings runs with `-Dmn.dev.compile=build-tool`, where Maven compiles each module as it is
configured.

== A filtered resource directory

A resource directory with `filtering` enabled is not read live, since the build expands it: the launcher reads its copy
from the class output, and a change to it is applied by `mvn process-resources` in `build-tool` mode.

[[bind-loopback]]
== Listening on localhost

`mn:dev` runs the application listening on `localhost` alone, so that a development server, with its development
settings and tools, is not reachable from other machines on the network. The manifest says
`micronaut.dev.bind-loopback=true`, and the launcher applies `micronaut.server.host=localhost` as the property source
of lowest precedence: a `micronaut.server.host` the application sets in `application.yml`, as the
`MICRONAUT_SERVER_HOST` environment variable or as a `-Dmicronaut.server.host` system property wins. `mn:test` is
unchanged.

To reach the application from a phone or a container, turn it off on the command line:

[source,bash]
----
$ mvn mn:dev -Dmn.dev.bindLoopback=false
----

or in the build:

[source,xml]
----
<plugin>
  <groupId>io.micronaut.maven</groupId>
  <artifactId>micronaut-maven-plugin</artifactId>
  <configuration>
    <bindLoopback>false</bindLoopback>
  </configuration>
</plugin>
----

[[control-panel]]
== Micronaut Control Panel

`mn:dev` adds https://micronaut-projects.github.io/micronaut-control-panel/latest/guide/[Micronaut Control Panel] to the
development runtime, served at http://localhost:8080/control-panel. The modules are added to the runtime classpath
of the development JVM only, versioned by the project's dependency management, the Micronaut platform BOM: the project's
own dependencies and what it packages do not change, and a module the application already declares, at its own version,
is not added again. Every launch gets the UI (`micronaut-control-panel-ui`), the management panels
(`micronaut-control-panel-management`) and the testing panels of continuous testing (`micronaut-control-panel-testing`).
The other panels are added when the runtime classpath holds a module they inspect:

[cols="2,3"]
|===
|Panel |Added when the runtime classpath holds

|`micronaut-control-panel-datasource` |`io.micronaut.sql:micronaut-jdbc`
|`micronaut-control-panel-hibernate` |`org.hibernate.orm:hibernate-core`
|`micronaut-control-panel-kafka` |`io.micronaut.kafka:micronaut-kafka`
|`micronaut-control-panel-object-storage` |`io.micronaut.objectstorage:micronaut-object-storage-core`
|`micronaut-control-panel-cache` |`io.micronaut.cache:micronaut-cache-caffeine`, `micronaut-cache-ehcache`, `micronaut-cache-hazelcast` or `micronaut-cache-infinispan`
|===

A Control Panel module that is not published yet, or that the dependency management does not version, is left out
with a message; any other resolution failure fails the goal.

The development runtime runs with these settings:

[source,properties]
----
micronaut.control-panel.enabled=true
micronaut.control-panel.path=/control-panel
micronaut.control-panel.security.access=ANONYMOUS
----

When the runtime classpath holds `io.micronaut.security:micronaut-security`, the access setting is left out: the
application's security decides who opens the panels.

They are written to `target/micronaut-dev/control-panel/micronaut-control-panel/micronaut-control-panel.properties`, a
directory of the runtime classpath, which Control Panel reads as its property source of lowest precedence: a setting
the application configures, in `application.yml`, as a system property or as an environment variable, wins.

To run without the Control Panel, turn it off on the command line:

[source,bash]
----
$ mvn mn:dev -Dmn.dev.controlPanel=false
----

or in the build:

[source,xml]
----
<plugin>
  <groupId>io.micronaut.maven</groupId>
  <artifactId>micronaut-maven-plugin</artifactId>
  <configuration>
    <controlPanel>false</controlPanel>
  </configuration>
</plugin>
----

`mn:test` adds no Control Panel: the tests start their own application contexts, as they do in the build.

[[micronaut-test-resources]]
== Micronaut Test Resources

With link:test-resources.html[Micronaut Test Resources] enabled, `mn:dev` and `mn:test` start the Test Resources
service before the launch, or connect to a shared one, as `mn:run` and `mvn test` do, and pass its connection settings
to the launcher's JVM as system properties. The service stays up for the whole session, through every reload and test
run, and is stopped when the goal ends, unless it is shared or was started with `mn:start-testresources-service`. When
the application does not declare `micronaut-test-resources-client`, the goals add it to the launch classpath, at the
version of the service. In a reactor, `micronaut.test.resources.enabled` and the other properties are read from the
application the goal runs, so an application can enable Test Resources on its own.

== Continuous testing

`mn:test` runs the project's tests on the same runtime, in test mode: see
link:test.html[Running tests continuously with `mn:test`].
